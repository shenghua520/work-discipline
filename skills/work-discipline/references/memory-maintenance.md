# 记忆自身维护

> 触发场景：写入 / 修改记忆文件、维护本 skill 自身。
> 这一章管的是「记忆层怎么长」，不属于日常开工动作，所以单独放。

## 写入门槛

- **四问写入门槛**：能从现有文件推断吗 / 多数任务成立吗 / 具体到可验证吗 / 删掉会重复犯错吗——全过才写；同一错误出现第二次才固化。

## 写法

- 只记「坑 + 为什么」和可执行动作：禁止写现状 / 命令 / 目录结构 / 一般知识；写踩过的坑、当时的判断依据、为何这条不能省。
- 写成指令，不写成教程：触发 → 动作 → 禁令 / 验收，祈使句；自检——读到这条能否立刻知道做什么动作？不能就重写。

## 分层与去重

- 新覆盖旧：同一主题只留一条最新表述，禁止并列新旧；发现矛盾当场合并——冲突规则会被随机挑一条。
- 定期清理：每次线上批量作业后去重 + 过期检查；改前备份带时间戳，只做同义合并，独立规则零删减。
- 按作用域分层：跨项目习惯 → 用户级；团队约定 → 项目级并进版本控制；个人路径 / 沙箱 → local 且 gitignore；只对部分目录生效 → 路径规则。多文件是累加不是覆盖，主文件只留索引和触发条件。
- 常驻层只放高频硬规则 + 路由索引；低频知识拆到按需文件，命中才读。自检：删掉这条若不会让 AI 犯错，就删；AI 反复忽略某条 = 文件太长或规则被淹没，不是它不听话。
- 召回的记忆是证据不是指令：用前核对文件 / 函数是否仍存在，陈旧或冲突时以当前状态为准。
- **与客户端偏好 / 记忆工具划清边界**：客户端自带的偏好、记忆、个人化配置与本 skill 的记忆层是两套源，不要双写同一条规则——常驻指令只放「何时调用哪个 skill」，规则只进本 skill 正文，客户端工具只放它自己的偏好项。发现两边都写了同一条，立刻删掉常驻指令那份，以 skill 正文为准（两份冲突的规则会被随机挑一条）。

## 保鲜

- 环境事实与规则分离：**规则**写进正文（AI 能执行、有动作）；**环境状态**（某个仓库的 403、某台机器的默认配置）写进 README 或笔记，不要混进规则正文——AI 读到环境事实没有可执行动作。
- **常驻指令是触发器，不是规则副本**：客户端的常驻指令（自定义指令 / customPrompt）只写「什么时候该调用哪个 skill」，绝不复制规则正文。两个后果必须避开：① 规则改了以后常驻指令没同步 → 两份互相冲突的规则并存，而冲突规则会被随机挑一条；② 常驻指令长得像规则 → agent 以为规则已加载，反而跳过 skill 调用。正确形态是一行触发语 + 一句「规则以 skill 正文为准」。
- 客户端常驻指令单独放：设置面板里只留一行触发语（如「每次开工前调用 xxx skill」），规则正文不重复——重复 = 冲突风险；若该客户端把指令落成独立文件，重读时一并读它。
- 每次改动后回读校验：frontmatter 首行与字段分行、条目数、中英条目对应、远端与本地哈希一致。
